# Nandina 1.0 Official Repository Promotion Plan

> Safe promotion of the accepted C++26 tree from `nandina_experiment` into the official
> `/workspace/Cpp/NandinaUI` repository.

## 1. Repository Roles

- `nandina_experiment` is the 1.0 implementation and validation source until the release candidate
  is frozen. After promotion it becomes the 2.0 experiment laboratory.
- `NandinaUI` is the official product, release, CI, documentation, and long-term maintenance source.
- `NandinaCLI` is the independent project-workflow product. It consumes published NandinaUI SDK
  metadata/artifacts but does not share the framework repository lifecycle or source tree.
- The final 1.0 release exists only after the promoted tree passes all acceptance gates in
  `NandinaUI`.

The repositories currently have independent histories and architectures. `NandinaUI` contains the
Zig Core + C ABI + language-binding line, while `nandina_experiment` contains the C++26 + Meson +
raylib line. Promotion is therefore a controlled mainline migration, not a normal file copy or a
set of same-history cherry-picks.

## 2. Safety Invariants

- Never promote from or into a dirty worktree.
- Preserve both repository histories in the official repository.
- Tag or branch the current official Zig line before changing its root tree.
- Do not delete the current untracked `NandinaUI/nandina_experiment/` directory until its origin and
  unique contents are audited.
- Do not force-push the official default branch as part of migration.
- Do not create the final `v1.0.0` tag in the experiment repository.
- The migration branch must be reviewable before it replaces the official default branch.
- The promoted source tree must be reproducible from a recorded experiment commit; no unrecorded
  manual edits may exist between the freeze and migration commits.

## 3. Required Freeze Points

Record immutable identifiers before migration:

| Repository | Recommended reference | Purpose |
| --- | --- | --- |
| `nandina_experiment` | `v1.0.0-rc1` | Exact accepted candidate tree. |
| `nandina_experiment` | `archive/1.x-experiment` | Read-only history of 1.x experimentation. |
| `NandinaUI` | `archive/zig-core` | Existing official Zig/Core+Bindings line. |
| `NandinaUI` | `migration/cpp-v1` | Review branch for the C++ 1.0 tree. |
| `NandinaUI` | `v1.0.0` | Final official release after validation. |

Names may gain a date or RC suffix if an existing reference conflicts, but their roles must remain
distinct.

## 4. Promotion Manifest

Before touching the official root tree, prepare a manifest containing:

- experiment repository URL, commit ID, tag, branch, and submodule commits;
- complete `git status`, `git submodule status --recursive`, and tracked-file inventory;
- supported compiler/Meson/Ninja/dependency versions;
- automated test result and Settings manual acceptance record;
- expected root files/directories after promotion;
- official files intentionally retained, renamed, archived, or removed;
- project/repository-name replacements required after import;
- release version and known limitations.

The manifest belongs in the official migration branch so later maintainers can reproduce why and
how the mainline changed.

## 5. Promotion Sequence

### P0. Freeze The Experiment Candidate

1. Complete all gates in `1.0_ACCEPTANCE.md` through C7.
2. Stop feature work; permit only release-blocking fixes.
3. Run a clean configure/build/test and external-consumer verification.
4. Commit the final documentation and promotion manifest inputs.
5. Create the experiment RC tag and archive branch.

### P1. Prepare The Official Repository

1. Review and commit, split, or otherwise preserve every existing official worktree change.
2. Audit the untracked nested `nandina_experiment/` directory against the frozen source repository.
3. Verify the existing Zig/C ABI build and tests at the archive point.
4. Create the official Zig archive reference.
5. Create `migration/cpp-v1` from the clean official mainline.

### P2. Connect Both Histories

1. Add the experiment repository as a temporary migration remote and fetch the frozen RC commit.
2. Create a migration commit whose ancestry records both the official pre-migration commit and the
   frozen experiment commit.
3. Make the migration commit's root tree equal to the frozen experiment tree before officialization
   edits. This avoids an opaque file-system copy while preserving both histories.
4. Review the tree inventory and confirm that no build cache, IDE state, local reference document,
   or nested repository was imported accidentally.

The exact Git commands are intentionally not embedded here: they must be generated from the
recorded commit IDs after both worktrees are clean and reviewed. The migration must not use a blind
recursive copy, force reset of an unreviewed worktree, or unrelated-history merge that leaves both
architectures interleaved at the root.

### P3. Officialize The Imported Tree

Apply a focused post-import commit series:

1. Rename the Meson project and user-facing repository references from experiment names to
   `NandinaUI`/the selected official package names.
2. Synchronize the SDK/release version and NandinaCLI compatibility metadata while keeping their
   independent version numbers.
3. Replace experiment-specific README/status language with official source-consumption and support text.
4. Keep public headers/resource helpers inside the accepted source SDK; do not introduce a
   system-installed SDK during promotion.
5. Add root license, changelog, CI, release notes, and promotion manifest.
6. Update submodule URLs and generated-project templates to consume the official repository/tag.
7. Publish the SDK manifest, full source bundle, hashes/signatures, and official source-index entry.
8. Update NandinaCLI's official-source fixture and compatibility tests without importing CLI source
   into the NandinaUI tree.

Keep migration mechanics, naming/metadata, build/distribution, and documentation changes in
separate commits when dependency order permits.

### P4. Validate In The Official Repository

Run the complete acceptance contract again from `NandinaUI`:

- clean default and fallback dependency builds;
- full automated suite and sanitizer lanes;
- generated application configure/compile/resource-package fixture;
- locked archive/wrap consumer plus external Git-submodule consumer fixtures;
- NandinaCLI official-index resolution, verified-cache, offline, and generated-project fixtures;
- Settings manual checks for input, CJK, resources, themes, resize, DPI, and teardown;
- source archive, offline consumer, and executable-relative portable staging checks promised by
  the 1.0 profile;
- `git diff --check`, tracked-file inventory, and submodule audit.

Any fix discovered here is authored in `NandinaUI`. Backport it to the experiment archive only when
needed to keep the frozen RC reproducible; do not reopen parallel 1.x development.

### P5. Release And Close The Migration

1. Review and merge `migration/cpp-v1` without rewriting away either parent history.
2. Create the official annotated `v1.0.0` tag.
3. Publish release notes with the Linux support profile and explicit non-goals.
4. Mark the experiment 1.x branch read-only in documentation.
5. Remove temporary migration remotes and local staging copies only after the official tag and
   remote branch are verified.

## 6. 2.0 Repository Model

After 1.0:

- Production fixes, API evolution, CI, source distribution, documentation, and releases happen in
  `NandinaUI`.
- `nandina_experiment` creates `experiment/2.0` from the same frozen C++ history and is used for
  high-risk components, backends, interactions, examples, and architecture spikes.
- A 2.0 experiment begins with a short contract: problem, non-goals, runtime object, ownership,
  event-loop phase, dirty flags, semantics, and acceptance evidence.
- An experiment is not automatically production code. After review it is either reimplemented in
  `NandinaUI` or promoted as small dependency-ordered commits that already meet official coding,
  documentation, testing, and compatibility gates.
- Official defects are never fixed only in the experiment repository.
- Avoid long-lived duplicated feature branches in both repositories; each feature has one active
  source of truth at a time.

## 7. Promotion Checklist

- [ ] Experiment C0-C7 acceptance units complete.
- [ ] Experiment worktree clean; RC commit/tag/archive branch recorded.
- [ ] Official worktree changes preserved; nested experiment directory audited.
- [ ] Official Zig line build verified and archive reference created.
- [ ] Migration branch preserves both histories and matches the frozen experiment tree.
- [ ] Official naming, versions, submodule URLs, documentation, license, and CI complete.
- [ ] SDK artifacts/index published and independently consumable by NandinaCLI.
- [ ] Full official automated and manual acceptance passes.
- [ ] Migration reviewed and merged without force-pushing history.
- [ ] Official `v1.0.0` tag published.
- [ ] Experiment 1.x archived and `experiment/2.0` role documented.
